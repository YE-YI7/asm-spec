# ASM direction: evidence-informed path selection

Date: 2026-09-22. Status: working direction agreed in discussion; product demand,
defensibility and economic benefit remain unvalidated. This document supersedes the earlier, narrower procedure-memory interpretation.
Historical exploration is not the current product boundary.

## Durable question

Given a goal and constraints, should the next unit of resources go to execution,
information acquisition, external assistance, or changing the system itself?

ASM originates in tool selection. Its prospective object is a feasible path to
an outcome, not a fixed category of component. A path may use a tool, model,
harness, skill, external service, delegate or a combination. Future paths could
include acquiring or building a capability and testing a system change. These
possibilities explain the long-term direction; they are not the current backlog.

The product boundary excludes turning ASM into a content store, memory platform,
conversation-continuity product, or universal RSI controller. Losing a repeatedly
corrected working style across windows is one motivating scenario, not the product.
Likewise, the components inside an agent do not define the ultimate conceptual
boundary. Capabilities can move between tools, services, other agents and weights.

## Near-term product hypothesis

Provide a host with less expensive, more comparable evidence for choosing an
execution path under the user's constraints. Help compare feasible alternatives
without requiring the host to repeat every discovery and validation step.

The prospective benefit is not a claim to reason better than the host. It is access
to relevant execution evidence at lower acquisition cost: observed availability,
account-specific price/access, comparable task outcomes and switching effort.
Whether ASM should expose that through a library, service, protocol or embedded
adapter is unresolved. "Evidence layer" names a hypothesis about value creation,
not a final packaging decision or a proven moat.

The user-visible moment should remain singular: when a path decision is needed,
the available alternatives, tradeoffs and uncertainty become clearer. Avoid
presenting three separate products or a universal autonomous decision-maker.

## Three horizons, one active scope

| Horizon | Question | Status |
|---|---|---|
| 1. Execution-path selection | Does reusable evidence improve today's path choice versus host rules or an ordinary agent with search? | Only active validation scope |
| 2. Capability acquisition | Should the system invoke, delegate, buy or build a capability? | Deferred / KILL LIST; no implementation commitment |
| 3. Improvement allocation | Which experiment or system change deserves the next exploration budget? | Deferred / KILL LIST; no implementation commitment |

Reopening horizons 2 or 3 requires credible horizon-1 feedback plus an explicit new
experiment and resource decision. No result here establishes general RSI readiness.

## Evidence lifecycle hypothesis

Collect permitted observations -> retain task/environment/version context ->
compare only supported cases -> inform a choice -> observe terminal results ->
write back new evidence -> refresh, down-weight or retire stale evidence.

This describes a desired closed loop, not a claim that the full pipeline exists.
A task fingerprint alone does not establish comparability. Failure, no access,
unknown price and incomplete outcome verification must survive aggregation.
Provider claims, direct observations and inferred judgments remain distinct.
Observed benchmark quality does not imply the same effect for another account,
model, task distribution or host. A receipt records a decision and its basis;
it does not by itself reserve funds, prove success or guarantee causal benefit.

Potential accumulation value comes from repeated, reusable observations, but data
rights, coverage, collection cost, freshness and reuse frequency determine whether
that value is defensible. Neither exclusivity nor resistance to platform entry is
established. Do not replace the old manual manifest burden with a larger one.

## Current experiment is not redefined

The existing internal development experiment remains unchanged: six task pairs;
accepted completion and elapsed time, full cost, and owner intervention;
predefined win/loss rules; September 25 18:00 Asia/Shanghai reporting deadline.
This public positioning note is not the full experimental protocol. Correction cost is a key
mechanism of interest, not a replacement for acceptance, full cost or elapsed time.

The Product Room frozen-facts comparison and the later network/persona protocols
are distinct experiments. V2/V3 do not silently replace this week's agreement.
Likewise, equal-source selector ablations or matched search in all arms would be
new diagnostics, not silent changes to the frozen-facts information contract.

The immediate test is whether access to reusable evidence provides net value, not
whether another agent or longer reasoning improves the answer. Charge acquisition,
refresh, verification, setup, retry and owner effort. First-cycle preparation costs
are fully charged; amortization requires observed reuse and a separate analysis.
The existing experiment measures the package's value; isolating evidence from
selector logic would require a separately specified ablation.

## What this direction does not assert

- A better problem formulation establishes demand.
- Competing hosts lack memory, evaluation, selection or control mechanisms.
- Evidence is the only possible business model or already exclusive to ASM.
- Model advances cannot reduce evidence collection or verification cost.
- More candidates necessarily justify another selector.
- The paper introduction or strategic agreement proves any performance benefit.

## Research anchors and next discussion

Rational metareasoning motivates evaluating resource use itself; intelligent
delegation expands alternatives beyond internal parts; self-improving-agent work
motivates future changes to the capability supply. These are research context,
not evidence of demand for ASM. Sources and a scoped problem formulation are in
`../../paper/path-selection-part1.md`.

See [public demand research](DEMAND-VALIDATION.md) for observed problems,
alternatives and outstanding validation. Do not expand architecture before
resolving the concrete decision point and evidence requirements.
